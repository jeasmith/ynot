# Count membership as a set and totals as a net signed sum

A Tag Total is one number standing for many transactions, and YNAB gives it several ways to mean more than one thing. Amounts are signed, so a reimbursement cancels the expense it repays. A transfer is stored as two linked transactions, so one movement of money can enter a tag twice with opposite signs. A hashtag can appear in a parent memo, in a split memo, or several times in both. The register is scoped to one account while a tag spans the budget. Each of these leaves a total that is arithmetically defensible and still misread, so the rules below fix a single interpretation for every displayed figure.

Membership is a set. A transaction belongs to a tag when that tag's identity appears anywhere in its memo text, and repeated occurrences make one membership carrying one contribution. Splits are read, not just displayed: a user who typed `#Home-Repair` into a split line in YNAB meant it, and a reader that ignored it would leave a tag whose total disagrees with what the user can plainly see in their own budget. What Ynot cannot do is write that memo, so such a membership is read-only — visible, counted, and honestly marked as beyond Ynot's reach.

The total is the plain net sum, with no class of transaction excluded and no filter narrowing it. Excluding income or transfers would make the total depend on a classification the user cannot see, and scoping it to the register would make the same tag show different numbers on different screens. The cost of netting is that a fully reimbursed tag reads as zero, which is why the net never appears alone: outflow subtotal, inflow subtotal, and member count travel with it, so a zero is always legible as activity that cancelled rather than activity that never happened.

## Consequences

- A transaction is a member of a tag when the tag's normalized, case-folded identity appears — under the [ADR 0004](0004-hashtag-memo-grammar.md) grammar — in the transaction's own memo or in the memo of any of its splits. That grammar is unchanged; only the set of memos it is applied to is settled here.
- Membership is a set rather than a count. A tag written in the parent memo and in three split memos of one transaction is one membership contributing once, which extends ADR 0004's rule for a repeated tag in a single memo to the transaction as a whole. Counting occurrences would silently multiply a Tag Total by how verbosely a memo was written.
- A membership carried only by split memos is read-only. Ynot writes parent memos alone, so such a membership cannot be removed, renamed, or deleted from Ynot; it is marked as such wherever it is listed, and excluded from the reach of bulk operations rather than being attempted and failing.
- Removing a tag strips it from the parent memo and then reports any membership that survives in a split. Dropping the transaction from the tag instead would be a lie with a short half-life: Ynot persists nothing, so the next full read restores the membership, and session-only undo cannot outlive the misstatement.
- A rename or delete likewise reaches parent memos only. Its impact preview counts the split-borne occurrences it cannot touch and states that the old spelling will remain in the vocabulary afterwards, so an operation that cannot fully succeed says so before it runs rather than after.
- The Tag Total is the net signed sum of its members' amounts, always displayed with its outflow subtotal, inflow subtotal, and member count. The composition is not optional detail: without it a net of zero and a tag with no transactions render identically.
- No class of transaction is excluded. Income and refunds are ordinary members whose positive amounts net against outflows, which is the question a tag on a reimbursable expense is usually asked.
- A transaction containing splits contributes its full signed parent amount, once, per [ADR 0001](0001-parent-only-tagging.md) — including when its membership came from a split memo. The tag is on the parent; the split is where the user happened to write it.
- Both sides of a transfer are ordinary independent transactions, tagged and counted individually. YNAB does not mirror a memo from one side of a transfer to the other, so a tag holds both sides only because a user tagged both, and when it does, the composition line names the pair. The zero is then explained rather than mysterious, and no rule has to guess which side of a movement of money the user meant.
- The membership universe is every transaction the budget returns: on-budget, tracking, and closed accounts alike. A tag applied years ago to a since-closed account still counts, because a total that quietly omits history is worse than one that includes a surprise the tag's transaction list can explain.
- Deleted transactions are never members, pending transactions cannot be because the API does not return them, and scheduled transactions remain out of scope for the first version.
- Unapproved transactions are ordinary members, taggable and counted. Tagging is organization, not approval, and the register's status facet already serves anyone who wants to separate them. A write must carry the transaction's current `approved` value or YNAB defaults it to unapproved; the research note records the constraint and the safe-write decision owns the mechanics.
- Every Tag Total is budget-wide and all-time. No register filter — account, year, search, category, or status — narrows it, and the first version offers no date control that would. A date-ranged total is reporting, which the map places out of scope, and it would multiply the interpretations of a single displayed number.
- No count or total appears without its scope stated beside it. The register's tag facet counts only the active account, so clicking a facet yields exactly as many rows as it advertised; the tag reader reads "all accounts · all time" and says how many members lie outside the active account. This is the form [ADR 0002](0002-active-account-register-scope.md) requires the account-scope tension to take: two numbers that differ, each labelled, rather than one number that is wrong on one of the two screens.
